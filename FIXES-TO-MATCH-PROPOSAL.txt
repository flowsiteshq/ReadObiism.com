SECTION A — CONTENT PROTECTION (the heart of the proposal)
----------------------------------------------------------
A1. [MISSING - CRITICAL] Stop bundling the book inside the app.
    Today the ENTIRE manuscript ships inside the app bundle as plain text
    (lib/book-data.ts = ~480 KB = full book). Anyone who downloads the
    APK/IPA can extract the complete text with zero effort. This single
    item defeats the whole "secure DRM reader" value proposition.
    FIX: Remove bundled chapter content from all app screens (reader.tsx,
    contents.tsx, quotes.tsx, principles.tsx, explore.tsx, account.tsx).
    Serve every paid page from the worker's /api/reader endpoint, which
    already validates the bound device hash before returning content.
    Keep only public metadata (chapter titles/numbers) in the bundle for
    the Contents screen.

A2. [MISSING - CRITICAL] Encrypted content delivery (AES-256).
    The worker's /api/reader returns book_sections.paragraphs_json as
    plain JSON over TLS. A user with a proxy or a rooted device can read
    the plaintext stream. Proposal requires: encrypted storage, key
    management, and decryption in memory / limited segments.
    FIX: Encrypt each section server-side (AES-256-GCM). Mint short-lived
    per-session content keys after license validation; decrypt in memory
    only; never persist plaintext to disk. Add key-rotation capability.

A3. [PARTIAL] Device binding is software-only.
    Current binding = SHA-256 device token stored in D1 reader_devices
    with a strict one-device check (409 on second device, 403 on wrong
    device). Good policy, but the token lives in plain localStorage /
    AsyncStorage — a rooted device or file copy can clone it.
    FIX: Generate a cryptographic keypair/secret in Android Keystore and
    Apple Secure Enclave (react-native-quick-crypto / expo-crypto +
    platform APIs), register the public part, and sign requests. Server
    verifies possession of the key, not just the hash string.

A4. [PARTIAL] iOS capture-response behavior.
    protected-reader.tsx already: prevents screenshots (FLAG_SECURE
    equivalent), blurs app-switcher preview (0.72), re-allows on exit.
    Proposal asks for capture-response mechanisms (detect recording,
    obscure content, notify server).
    FIX: Add expo-screen-capture's screenshot/screen-recording listeners:
    on detection, hide content, log an event to the server, show a
    notice. Still worded as deterrence, not guarantee.

A5. [MISSING] Watermarking.
    Proposal lists watermarking under security scope (release-plan too).
    FIX: Stamp per-reader watermarks (email/device id, faint diagonal or
    per-paragraph invisible markers) into delivered content so leaked
    text can be traced back to the source device.

A6. [MISSING] Offline access design.
    Reader currently needs the server; bundled content was the accidental
    offline path, and A1 removes it.
    FIX: Define offline policy (e.g., cache encrypted sections for X days
    with periodic license revalidation). Proposal explicitly lists
    offline licensing as a decision point — needs the owner's call.

A7. [PARTIAL] Content ingestion pipeline (Bonus 3).
    scripts/import-manuscript.mjs parses the approved manuscript into
    structured chapters (lib/book-data.ts). Works, but outputs plaintext
    into the app bundle (see A1).
    FIX: Extend the pipeline to package the manuscript into the
    ENCRYPTED D1 book_sections store (encrypt + upload step), so the
    same approved workflow feeds the protected delivery path.


SECTION B — ACCOUNTS, DEVICES & LICENSES (Tier 1 basic / Tier 2 enhanced)
------------------------------------------------------------------------
B1. [PARTIAL] One-device policy — enforcement exists, lifecycle does not.
    Working today: first-device binding on purchase ("Allow first-device
    binding" commit), second-device rejection, UNBOUND rebind path.
    MISSING: any way for a legitimate buyer to MOVE their license when
    they change phones (the exact flow in Proposal Section 3: deactivate
    old -> validate -> activate new) and no replacement limits.
    FIX: Add account-scoped endpoints: GET device list, POST deactivate
    (with email verification), configurable replacement cap (e.g., 2 per
    year), and an audit trail. Decide: self-service vs support-only
    (still pending owner decision).

B2. [PARTIAL] Mobile app is not connected to the entitlement system.
    The native app's auth (hooks/use-auth.ts, app/oauth/*) talks to the
    tRPC/Express server and Manus OAuth — which needs OAUTH_SERVER_URL
    and is unconfigured. The real purchase/entitlement data (Stripe,
    devices, accounts) lives in the Cloudflare Worker + D1.
    FIX: Point the mobile app at the worker endpoints (register/login/
    account/access/reader/claim) OR unify backends. This is the
    architecture decision we paused earlier.

B3. [MISSING] Password reset & account controls.
    Worker has register/login with salted hashes but NO password-reset,
    no email verification, no account deletion endpoint for the native
    app (Google policy requires in-app account deletion).
    FIX: Reset-by-email flow, email verification at registration,
    native account-deletion path (web has delete-account.html already).

B4. [MISSING] Session & abuse controls.
    Sessions exist with expiry, but no concurrent-session limit, login
    anomaly monitoring, or rate limiting on auth/checkout/claim routes.
    FIX: Per-account session cap, rate limits per IP/account, anomaly
    log (failed logins, device-claim conflicts).

B5. [MISSING] Root / jailbreak risk handling.
    FIX: Detect rooted/emulator/hooked environments (expo-device +
    native checks); degrade gracefully (warn, restrict offline cache,
    log) — per release-plan wording, never claim prevention.

B6. [MISSING] Audit logging.
    FIX: Structured log of license events (purchase, bind, rebind,
    deactivation, capture-detection, admin actions) — prerequisite for
    Enterprise "audit records" and support disputes.

SECTION G — INTERFACE, VISUAL SYSTEM & ACCESSIBILITY (added Oct 28, 2026)
------------------------------------------------------------------------
Previously excluded from this list; now tracked here. Applies to the Expo
app (iOS / Android / web) unless a line says otherwise.

G1. [DONE] Brand system unified across the whole app.
    Before: reader, contents, explore, account, quotes, principles,
    profile and the in-app website still used the old template palette
    (navy #151A52, coral #FF5B55, lime #DFFF4F, sky #6CD9FF), matching
    neither the landing page nor the welcome screen.
    After: one palette everywhere — ink #0B0F14, gold #E9C46A, bronze
    #9A6E1B, cream #FFF6E7, warm borders #E3DCC8. Theme tokens
    (theme.config.js) and the tab bar were updated to match, so native
    navigation and system surfaces inherit the brand automatically.

G2. [DONE] Contrast raised to WCAG 2.2 AA.
    - Reader back-navigation label        3.9:1  -> 6.9:1
    - Reader eyebrow (accent on cream)    3.3:1  -> 4.6:1
    - Saved-bookmark icon on its fill     ~2.0:1 -> ink on gold
    - Chapter eyebrows, result counts and section labels moved to the
      darker bronze wherever text sat on cream.

G3. [DONE] Touch targets raised to 44x44 or larger.
    Welcome film/play, menu and close controls; reader back, contents and
    bookmark controls; account sign-in/out, goal pickers and saved-passage
    button; explore filters and reset control.

G4. [DONE] Micro-typography legibility.
    Labels that were 7–8 px (film status, discovery labels, footer motto,
    progress captions, reader meta) are now 9–11 px with adjusted tracking.
    Reader type scale extended from 18/20/22 to 18/20/22/24/26 px so
    low-vision readers can enlarge the text.

G5. [DONE] Welcome screen composition (web + native).
    - The cinematic film was effectively invisible: a 94%-opacity portrait
      covered the full screen above the video, and a flat full-screen veil
      dimmed what remained to roughly 14% brightness. The portrait is now
      ghosted and the veil is a directional gradient, so the film reads as
      moving behind the type.
    - Desktop web: primary and secondary actions sit side by side, and the
      discovery rail and footer span the content width with a hairline
      rule — matching the landing page's editorial structure.
    - Short screens (under 720 px tall): compact type and spacing prevent
      content clipping on iPhone SE-class devices.

G6. [DONE] Reader reading experience.
    Drop cap, deck, progress card and reflection card share the brand
    palette; progress track and fill have AA-passing separation; the saved
    bookmark state has a readable active style.

G7. [DONE] Account access UI.
    New sign-in / create-account card on the "My Edition" tab with live
    edition status and sign-out, wired to the worker endpoints described
    in B2. Shows "PREVIEW EDITION" vs "LICENSED EDITION" in the reader.

G8. [PARTIAL] Landing page (gh-pages).
    Relative-link fixes are applied so the static site works from a
    subfolder as well as from the domain root (sign-in, reader, privacy,
    delete-account and back links). The typography / touch-target / focus
    / reduced-motion polish for this page was reverted after a build-script
    incident and must be reapplied and verified item by item.

G9. [MISSING] On-device visual verification.
    The re-skin has been verified by code review and one desktop web

G10. [MISSING] Native reduced-motion and screen-reader pass.

G11. [MISSING] Store screenshot set.
